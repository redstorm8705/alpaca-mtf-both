*   **CRITICAL | `execution/portfolio_tracker.py` | P&L Inconsistency in `all_time_stats`** | The `all_time_stats` block in the `EOD SNAPSHOT` exhibits internal arithmetic inconsistencies. Specifically, the reported `profit_factor=3.55` conflicts with `avg_win=27.06` and `avg_loss=-13.56` (which yield a profit factor of `1.99`). This indicates a fundamental flaw in how these summary statistics are calculated or aggregated within `PortfolioTracker.get_stats()` or `write_eod_summary()`, leading to a misrepresentation of overall performance.
*   **CRITICAL | `execution/portfolio_tracker.py` | `_BotEncoder` Fix Incomplete for UUID** | Despite the `_BotEncoder` being implemented in `execution/portfolio_tracker.py` to handle `UUID` serialization, the `ERROR | Object of type UUID is not JSON serializable` log reappears for `eod_YYYY-MM-DD.json`. This implies either the `_BotEncoder` isn't consistently applied to all JSON serialization points that might involve `UUID` objects (e.g., when saving `eod_YYYY-MM-DD.json`), or a `UUID` object is being introduced in an unexpected data structure that bypasses the encoder.
*   **HIGH | `main.py` | `_entry_confirm_buffer` and `_conviction_streak` not reset daily** | The global state variables `_entry_confirm_buffer` and `_conviction_streak` (used for multi-scan entry gating, seen in `ANOMALY-2` logs) are not explicitly cleared in `main.py`'s `_daily_reset()` function. This can lead to these counters accumulating across trading days or bot restarts, potentially blocking otherwise valid entries indefinitely (if a symbol only qualifies for a few scans before a daily reset, and then accumulates on subsequent days without a proper reset). This is particularly problematic given the `ANOMALY-2` logs warning of "permanently blocked" entries.
*   **MEDIUM | `midday_audit.py` | Inconsistent Timezone Handling for Audit Date** | The script uses both `AUDIT_DATE` (local PT date) and `AUDIT_DATE_ET` (ET date) to filter trade events and logs. This dual-timezone approach, relying on string `startswith()` for filtering, can cause off-by-one-day errors or missed events during timezone transitions (e.g., around midnight ET when it's still the previous day in PT). All date-based filtering and comparisons should be standardized to a single timezone, preferably ET for consistency with Alpaca's timestamps.
*   **LOW | `execution/broker.py` | `cancel_open_orders_for_symbol` Silent Failure** | The function `cancel_open_orders_for_symbol` unconditionally increments its `cancelled` counter for each order it attempts to cancel, regardless of the `bool` return value of the underlying `cancel_order` call (which can return `False` on failure). This can lead to an inflated count of "freed" orders and mask actual failures in cancelling orders.
*   **LOW | `execution/broker.py` | `close_position` Fractional Share Edge Case** | The `close_position` function relies on Alpaca's API to close an entire position implicitly. If a position holds a very small fractional quantity of a share (e.g., `0.0001` shares), the implicit "close all" request might fail if Alpaca requires an integer quantity or a quantity above a minimum threshold, potentially leaving tiny residual positions stranded. Explicit handling or rounding for such edge cases would enhance robustness.

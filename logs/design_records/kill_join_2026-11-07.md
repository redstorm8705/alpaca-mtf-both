## Rev 4 — the design to approve (2026-11-07, signed: Claude)

**Why the bound was dropped.** Round 3 gave the same failing shape from Codex, Taleb and Thorp. A protected buy made
after the last full ledger rebuild is invisible to any bound that uses the ledger file's write time. Other writers
(QHM and F6 single-row updates, `reconcile_drift`) move that time without folding the buy in. Example: QHM buys 9 at
$100 at 10:00, another writer saves the file at 10:01, and the check at 10:02 reports $0 against a true Day+Swing of
-$18. The only safe answer is to keep the exact measure and make the ledger catch up quickly.

**What changes (three parts; the 7% measure itself does not change):**
1. **Crash fix (all reviewers agreed).**
   - `can_open_position()` catches the kill check's RuntimeError, logs ERROR `[change=kill-join-1107]`, records the
     fault on the RiskManager and returns False.
   - entry_logic.py:727 reads the recorded fault instead of calling `check_kill_switch()` again, so the entry loop
     breaks as "kill active" and never reaches the power-hour expansion branch.
   - The recorded fault clears at the start of every `check_kill_switch()`.
   - Tests: an entry loop whose kill check raises on every call returns with no exception, zero entries and one check
     per attempt.
2. **Every unresolved join logs its reason** once per distinct reason, with the symbol, which of the three checks, and
   the ledger and broker quantities. Today these paths are silent.
3. **The ledger is rebuilt on demand.**
   - On an unresolved join, the kill check writes a small request file `data/state/ledger_rebuild_request.json`
     (atomic tmp → replace, no network, at most once per minute per process).
   - `run_ledger_sync.py --if-requested` exits at once unless a request is newer than its last completed run.
     Otherwise it runs the existing full rebuild (`sync_ledger`, unchanged, with its refuse-to-shrink guard), under a
     non-blocking lock so two rebuilds never overlap.
   - A new OCI cron line runs `--if-requested` every minute on weekdays. The existing 20-minute rebuild stays.
   - A rebuild takes 17-21 s (ledger_sync_cron.log, 11-06), so the next kill check after a fill is exact again within
     about 1-2 minutes instead of up to 20.
   - The run writes `last_rebuild_utc` into the streak file (written only by this runner). That gives the forward
     build a trustworthy watermark.

**What stays blocked, by design:** while the join is unresolved, new entries stay paused, exactly as today. A rebuild
that refuses a protected-floor shrink (needs the operator) keeps the pause until it is confirmed. That is the
existing control, not a measurement fault.

**Expected effect:** on 11-06 the 10:14 ET NVDA buy would have blocked entries for about 1-2 minutes instead of 46. No
change to any P&L figure, threshold or latch.

**Reversal:** a pause after a fill that lasts longer than two rebuild runs with no refusal logged, or any change in a
replayed kill measure.

## Rev 4.1 — round-4 implementation requirements folded (2026-11-07, signed: Claude)
1. **One lock for every rebuild** (Codex 1, Thorp 3): the scheduled 20-minute run, `--if-requested`, manual and startup
   runs all take the same non-blocking file lock. A run that finds it held logs "busy; request remains pending",
   leaves the request untouched and exits 0 (Codex 5).
2. **A watermark only for a completed rebuild** (Codex 2, Thorp 1): `last_rebuild_utc` is the time captured just
   before the fill fetch. It is written to the streak file only when `sync_once()` returned healed=True, after the
   ledger's atomic replace. A refused shrink or an exception never advances it.
3. **No lost requests** (Codex 3, 4): each request carries a generation id (time plus a random token). The runner
   records the generation it started from. After a healed run it marks only that generation done, so a request
   written during the run stays pending for the next pass. Writers use a unique temporary name, then `os.replace`.
4. **Back-off during a refusal** (Thorp 2, Taleb N1): an on-demand run is skipped while the last run was refused and
   no new fill or order change has appeared since; the 20-minute schedule still runs. Only scheduled runs count
   toward the 3-run "ledger may be stale" page, so the page timing is unchanged.
5. **Metric logging** (Taleb N4): each exact check after a request logs the minutes since that request
   `[change=kill-join-1107]` (the Q40 metric).
6. **Tests:** the entry-loop crash test (one check per attempt), two overlapping rebuild runs, a request written
   mid-run, lock contention, and refusal back-off.
7. **Stale earlier text:** the rev 1-3 answers and the "Expected effect and reversal" section below describe the
   dropped measure and are superseded by Rev 4 and this section.
8. **Not in this design (forward build, to the owner next):** two exact-path masks that predate this design and that
   rev 4 does not change. Both close only with the rebuild watermark in item 2 plus a time-aware join (any
   QHM/F6-tagged fill after `last_rebuild_utc` treated as unresolved):
   - Codex's equal-net changed-split case;
   - a protected buy after the last rebuild on a symbol with no ledger row.

## What happened (measured 2026-11-07 from OCI logs/mtf_bot.log, day_tier_runner_cron.log, ownership_ledger.json)

- `OWNERSHIP_GUARD_ENFORCE = True` since commit 6e9a7448 (2026-11-05, "Activate F6 ownership guard prerequisite").
- With the guard on, `RiskManager._intraday_trading_pnl` (execution/risk_manager.py:1302-1489) requires the ownership
  ledger (`data/state/ownership_ledger.json`) to agree exactly with the broker at every kill check. Three of its checks
  return `(0.0, False)` WITHOUT logging a reason:
  1. a ledger row's net quantity differs from the broker's position (line 1404);
  2. a non-flat ledger row has no broker position (line 1430);
  3. a QHM- or F6-tagged fill today on a symbol the ledger shows flat (line 1447).
  `check_kill_switch` then raises `RuntimeError("kill-switch exact tier attribution is unresolved")` (line 1560).
- The ledger is rebuilt by `run_ledger_sync.py` every 20 minutes (OCI cron `*/20 13-21 * * 1-5`). Any fill between
  rebuilds can break the join until the next rebuild. Its `last_reconciled_utc` field is `None` (never stamped by
  sync_ledger), so the kill check cannot tell which fills came after the rebuild.
- **2026-11-06 (RTH):** QHM bought 1 NVDA at 10:13:58 ET (ledger NVDA flat → check 3). The kill check failed from
  10:14 to 11:00 ET: 6 `run_cycle` checks and 19 Day-tier checks logged "no new entries (fail-closed)"; one cycle
  crashed at 10:16 ET ("Loop error", traceback main.py:1136 → run_cycle.py:2216 → entry_logic.py:723
  `can_open_position()` → check_kill_switch) because `execute_entries` does not catch the raise. Failures stopped
  after the 11:00 ET ledger rebuild. QHM's GE buy (10:44 ET) and a Day exit (10:46 ET) fell inside the same window.
- **2026-11-05 after the close:** 6 failures 4:04–6:45 PM ET; 11-06 00:17–07:32 UTC 14 more (no ledger rebuild after
  17:40 ET; the NVDA QHM stop-out left the ledger behind the broker overnight).
- Before 11-05: zero occurrences of this error in mtf_bot.log.

So on every session in which any tier trades, new entries for every tier can stop for up to 20 minutes after a fill,
and longer when a rebuild refuses a protected-floor shrink pending operator confirmation (11-05 GE/NVDA: refused
streak 12-22).

## Design

1. **Fall back to the existing per-symbol measure (KILL-ATTR-1023) instead of raising.** When the guard is on and one of the
   three join checks fails (or `_protected_held_qty()` returns None), `_intraday_trading_pnl` computes the
   KILL-ATTR-1023 tiered measure (`_intraday_trading_pnl_tiered`, lines 1037-1199) on the same fills and positions.
   That measure (a) removes protected shares only for ledger rows that match the broker, (b) for every other symbol
   uses the MORE NEGATIVE of "broker qty minus QHM's own count, protected fills skipped" and "count every share and
   fill", and (c) reports `exact=False`. It is the measure the bot used with the guard off until 11-05.
   `check_kill_switch` then evaluates the 7% limit on it as usual; `attribution_exact` stays False, so the typed
   verdict cannot be GENUINE_TRADING_LOSS-exact and the F6 starter bypass stays closed (F6 is off anyway).
   If the tiered measure itself fails, or the ledger file is unreadable, the existing raise stays (entries pause).
2. **Every unresolved join logs its reason once per distinct reason** (symbol, which check, ledger vs broker
   quantities) with tag `[change=kill-join-1107]`. Today these three paths are silent.
3. **`can_open_position()` catches that RuntimeError** and returns False with an ERROR line, so a raise inside
   `execute_entries` blocks entries for that cycle instead of aborting the cycle (the 10:16 ET crash).
   `check_kill_switch()` itself is unchanged for its direct callers (run_cycle.py:301 and run_day_tier.py:1267 already
   turn the raise into an entries-only block).

Not in this design (forward build, separate diff): stamp `last_reconciled_utc` with the fills snapshot time in
`sync_ledger` and make the exact join time-aware (ledger + protected-tagged fills after the stamp), so the exact path
holds between rebuilds. That changes the ownership guard, which has its own owner approval; it goes to the owner
separately.

## Rev 2 — the reviews of rev 1 folded (2026-11-07, signed: Claude)

**Why rev 1 failed (three reviewers, three concrete inputs, all reproduced from the code):** the tiered measure's
"count-all" candidate includes protected (QHM/F6) shares and fills, so a protected GAIN can offset a Day/Swing LOSS:
- Codex: ledger XYZ qhm 90, broker 100, Day buys 10 @ $120, prior close $100, now $102, no QHM count. Count-all
  reports $0; the true Day P&L is -$180 (-7.2% of $2,500: a missed trip).
- Taleb (a): Day short 10 @ $198, QHM buys 1 @ $195 (its state count stays 0 until its fill check), now $210.
  Reported -$105; true -$120.
- Taleb (c): ledger QHM 3 + Day 2, QHM stop sells 3 @ $210, now $185, QHM count stale at 3.
  min(count-all 0, state-based +15) = 0; true -$30.
- Thorp: catching the raise in `can_open_position()` alone does not stop the crash: entry_logic.py:727 calls
  `check_kill_switch()` again with no catch.

**Rev 2 measure — a provable lower bound, not a choice between estimates.** When the guard-enforced exact join fails,
each symbol is measured as follows. Symbols whose ledger row matches the broker keep the exact computation.
- Fills: every fill tagged QHM or F6 belongs to the protected tiers and is left out. Every other fill (Day, Swing,
  intraday and untagged, except the untagged buys below) is counted, repriced from prior close as today.
- Open leg: the Day+Swing share count `a` lies in `[q - Pmax, q]`, where `q` is the broker's signed quantity and
  `Pmax` = the ledger's protected claim for the symbol (0 if no row) + today's QHM/F6-tagged buys. Protected tiers are
  long-only and grow only by buying, so the true protected count is in `[0, Pmax]` (a protected sale only lowers it).
  `(current - prior close) × a` is linear in `a`, so its minimum over the interval is at an endpoint: open leg = the
  smaller endpoint.
- Untagged buys on a symbol with `Pmax > 0` (an owner's manual add may belong to a protected tier): each such share is
  either all Day/Swing or all protected, so it counts `min(0, current - its fill price)` and is left out of `q` and of
  the fill terms. If those shares exceed the broker's long quantity (some were sold again today), the bound cannot be
  formed and the existing raise stays.
- Symbol P&L = that minimum + the counted fill terms. It is never above the true Day+Swing P&L for any allocation of
  the protected shares inside `[0, Pmax]`.
- Checked by hand: Codex's case gives -$180 (truth -$180), Taleb (a) -$120 (truth -$120), Taleb (c) -$30 (truth -$30).
- Not priceable (no prior close on a non-flat open leg, or a fully closed held-over lot) → the existing raise (entries
  pause), unchanged. Ledger file, fills or positions unreadable → the existing raise, unchanged.
- `attribution_exact` is False on this path in every case (Taleb R2); the F6 bypass stays closed.
- Positions are fetched before the `_protected_held_qty() is None` early return so the bound can run (Thorp, Taleb R3).

**Rev 2 crash fix (Thorp):** the kill check's RuntimeError is caught in `can_open_position()`, which returns False,
logs an ERROR line and records the fault on the RiskManager. entry_logic.py:727's second call reads that recorded
fault instead of calling `check_kill_switch()` again. A fault therefore breaks out of the entry loop as "kill active"
and never falls through to the power-hour expansion branch. entry_logic.py joins the Covers list.

**Tests (Taleb R4):**
- The three reviewer cases.
- A randomized property test (random positions, fills, ledger claims and true allocations) asserting bound <= true
  Day+Swing P&L.
- An `execute_entries` test that raises on every kill check and asserts no exception and zero entries.

**Forward build (unchanged, separate approval):** stamp `last_reconciled_utc` in `sync_ledger` and make the exact join
time-aware, so the exact path holds between rebuilds and the bound is rarely needed.

Corrected answers:
- Q12: never-mask-a-loss holds by construction (a lower bound over every allowed allocation), proven by the property
  test, not by "the more negative of two estimates".
- Q18: rev 1 called the KILL-ATTR-1023 measure safe because it had been approved before. The reviews showed it masks a
  loss when the ledger is stale, so rev 2 does not reuse it.
- Q28: the bound uses the positions and fills of the same check; positions are now fetched before the early return.

## Rev 3 — round 2 folded (2026-11-07, signed: Claude)

Round-2 findings, each reproduced from the code and the arithmetic:
- **Codex (reject):** a ledger row whose net equals the broker can still hide a changed split. Example: QHM 9 + Day 1
  in the stale ledger, then QHM buys 1 and Day sells 1, so the net stays 10. The exact path reports Day +$10; the truth
  is $0, and it scales without bound.
- **Taleb C1:** an untagged SELL of protected shares (an owner trim, or a legacy tagless stop) above prior close
  offsets a Day loss: $0 reported against a true -$30.
- **Taleb C2:** a malformed ledger row must not be read as "0 protected".
- **Thorp A:** a protected buy on an earlier session after the last rebuild is in neither the ledger nor today's fills:
  -$160 reported against a true -$180.
- **Thorp C:** the lower bound counts protected shares' losses as Day losses on a broad down day, which could latch a
  false all-day kill.
- **Codex/GAI:** the crash fix needs a test that the kill check runs once per entry attempt, and the recorded fault must
  clear at the next check.

Rev 3 measure, used only when the exact join fails:
1. **Every symbol is measured by the bound** (none keeps the exact path), so equal nets prove nothing (Codex).
2. `Pmax` = the ledger's protected claim + QHM/F6-tagged buys since the ledger file was last written. The bound runs
   only when that write time is on the current PT date, so today's fills cover the gap (Thorp A); otherwise the
   existing raise stays. [hypothesis — unverified: the file's write time stands in for the rebuild time until
   `last_reconciled_utc` is stamped (forward build). Tier managers that write the ledger between rebuilds only move
   the time later, and fills before that time are already in it.]
3. Open leg: Day+Swing shares `a` in `[q - Pmax, q]` (q excludes the untagged buys of item 4); the bound takes the
   smaller endpoint of `(current - prior close) × a`.
4. On a symbol with `Pmax > 0`, each untagged buy share counts `min(0, current - its fill price)` and each untagged
   long-sale share counts `min(0, its fill price - prior close)` (Taleb C1). Untagged `sell_short` / `buy_to_cover`
   shares cannot be protected (protected tiers are long-only) and count in full. QHM/F6-tagged fills are left out.
   If the untagged-buy shares exceed the broker's long quantity, the bound cannot be formed and the raise stays.
5. A row that exists but cannot be parsed (`_protected_held_qty()` None for a malformed row) raises, unchanged (C2).
6. **Two-sided verdict (Thorp C):** the same construction with the larger endpoints gives an upper bound.
   - Upper bound breaches 7% → the loss is certain under every allocation: the kill latches as today, persisted with
     `attribution_exact=False`.
   - Only the lower bound breaches → entries are blocked for this check only, as a CONTROL_FAULT entries block
     (no latch, nothing persisted as GENUINE_TRADING_LOSS), and the next check re-evaluates.
   - Neither breaches → entries allowed.
7. Every bound check logs one line per distinct reason with the symbols, each symbol's `Pmax`, the interval endpoints,
   the untagged share counts and both bounds `[change=kill-join-1107]` (GAI, Taleb).

Crash fix (unchanged from rev 2, plus two items):
- The recorded fault is cleared at the start of every `check_kill_switch()`.
- A test asserts the check runs exactly once per entry attempt in `execute_entries`.

Property test generator: random positions, fills (tagged, untagged, offsetting), stale ledger rows, protected buys
since the ledger write, and true allocations. Assertion: lower bound <= true Day+Swing <= upper bound on every draw,
plus every reviewer case above.

Corrected answers:
- Q11: on a broad down day an unresolved check may block entries for that check (lower-bound breach); it never latches
  unless the upper bound also breaches.
- Q13: ledger written before today → raise (unchanged).
- Q40: a machine check on replay: lower <= exact measure <= upper on every replayed check where the exact measure is
  computable.

## Expected effect and reversal (front-loaded replay, to run before ship)

Replay `check_kill_switch` on 2026-11-05 and 11-06 from the logged fills, positions and ledger snapshots: expected
zero "exact tier attribution is unresolved" raises; the tiered measure's value at each failed check is within the
kill limit (account Day+Swing realized +$31.12 on 11-06; no loss near 7%). Wrong if, on any replayed check where the exact measure is computable, the lower bound is above it or the upper
bound is below it.

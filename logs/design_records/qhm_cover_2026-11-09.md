a dip-add does not drop the old stop before the buy fills; a stop-failure alert is never hidden after a new buy).

## 1. Incident (measured 2026-11-09, Alpaca orders + server logs + state)
- NVDA at Alpaca: 3 shares long, zero open orders, so no stop (Alpaca positions/orders API, 17:3x UTC).
- Orders today: 15:05:49 QHM buy 1 @ 178.05 limit, filled 15:05:50; 15:44:12 sell stop 1 @ 163.07, cancelled 15:53:23; 15:53:23 QHM
  buy 1 @ 179.49 limit, filled 15:53:24. Both replacement stops were rejected by Alpaca's wash-trade rule (broker.py:1352, a sell stop
  is refused while a buy rests). The 15:53 failure sent no Slack page: alerts.py:625-642 keeps one page per (symbol, side, stop price)
  per ET day in `data/state/gtc_failed_pages.json`, which already held `NVDA|sell|163.07|slack` from 07:05 PT.
- Since 15:53 every QHM cycle logs "NVDA exact QHM quantity proof unavailable; keeping PENDING_STOP_REPLACE" (13 times by 17:40 UTC)
  and places nothing. State: `qty_filled 2`, `stop_order_id null`, `ambiguous_add_client_order_id null`, `stop_recovery_baseline_qty 1`,
  `stop_recovery_add_submitted true`, `dip_adds_quarter 0`, `last_dip_add_date null`. Ledger: alpaca_net 3, qhm 2, intraday 1.

## 2. Root cause (file:line on origin/main 4b5658e)
1. `TIER_CAPITAL_ALLOCATOR_ENABLED = False` (config.py:1031) → the add has no lease → `live_order_id(None)` returns None
   (tier_capital_allocator.py:1091) → `_add_coid = None` (quarterly_hold_manager.py:2874). The broker gives the buy its own `QH-…` id,
   and QHM's submit check rejects it (`coid != _add_coid`, :2928). QHM then skips the recover-by-id loop (needs an id), skips the
   fill poll, and re-places the stop at once while the buy still rests → wash-trade reject → PENDING_STOP_REPLACE. Every QHM add has
   taken this path since the id check landed (f4357146, 2026-10-16).
2. Because the add "returned 0 filled", the anti-repeat counters (`dip_adds_quarter`, `last_dip_add_date`, :2791 caller) were never
   written, so a second dip-add fired 48 minutes later.
3. The strict recovery in `resubmit_stop_if_needed` (:1494) expects QHM to own `baseline − stop filled` = 1 share and compares that
   with the ledger (2) in `_strict_resync_qty` (:5136); the add's fill is never counted, so the proof fails every cycle, forever. No
   path places a stop on the quantity QHM can prove.
4. The alert day-stamp is never cleared by a later successful stop, so a second failure the same day is silent.

## 3. The fix
A. **Every add carries a QHM order id.** In `_stop_safe_add`, when there is no lease, `_add_coid` is a fresh QHM client order id in
   the same format the broker uses (`ownership_guard.make_coid("qhm", symbol, "buy", …)`), passed to the buy submit. The existing
   flow then runs as designed: submit check passes, the fill poll runs, the ledger is credited with the exact order, and the stop is
   re-placed only after the buy is filled or cancelled. A lease present behaves exactly as today.
A2. **A submitted add counts.** `last_dip_add_date` (and `dip_adds_quarter`) are recorded whenever the buy reached the broker, not only
   when the poll proves a fill. Same for the tranche-add caller that uses `_stop_safe_add`.
B. **Recovery covers the shares QHM can prove.** In the strict branch, when `stop_recovery_add_submitted` is true:
   - add id known → the existing ambiguous-add branch (baseline + that order's fill) is used instead of the survivor-only check;
   - add id null (old state, like NVDA now) → QHM's quantity is proved from fills: QHM-tagged (`QH-` client id) buy fills minus
     QHM-tagged sell fills on the symbol since the hold's `created_at`.
   Cover quantity = min(that, broker long quantity − shares other live tiers claim (the same sources `unmanaged_positions` uses) −
   open sell orders on the symbol). So the stop never exceeds the position and never double-covers an owner's manual stop. The ledger
   is credited for those exact order ids before the stop goes in; the stop is placed through the existing `_recover_or_submit_stop`;
   the recovery fields are cleared. Any unreadable input → stay pending and page (as today).
C. **Alerts.** A successful stop for a symbol and side clears that symbol/side's day stamp in `gtc_failed_pages.json`, so a new failure
   pages again.

Expected on deploy, with today's NVDA state and no manual stop: one GTC sell stop for 3 shares at $163.07, ledger QHM 3, state ACTIVE.
With an owner stop for 3 already resting: cover quantity 0, no second stop, recovery cleared, logged.

## Changes after review round 5 (Codex APPROVE-WITH-CHANGES on round 4)
- **No ledger write in the legacy recovery.** B's "credit the ledger" step and T2 are superseded: the recovery for old ambiguous state
  never credits, debits or rebooks the ownership ledger. Fix A's normal add path keeps today's exact-order credit
  (`apply_authorized_tier_fill_increase` after a proven fill). Test: today's NVDA state leaves the ledger at qhm 2 / swing 1.
- **One cover formula:** cover = min(proved, QHM's ledger claim, broker long − Σ remaining quantity of valid resting protective sells).
  Other-tier claims are not subtracted (a stop at the broker protects shares regardless of which tier owns them; the QHM ledger cap
  keeps QHM within what it owns). Gap = broker long − Σ remaining protective sells − cover; a gap > 0 sends the ACTION page.
  NVDA now: min(3, 2, 3 − 0) = 2, gap 1 → stop 2 + ACTION page for 1. Owner stop 1 resting: min(3, 2, 2) = 2, gap 0. Owner stop 3:
  cover 0, gap 0, one heads-up. Every zero-cover decision logs its reason.
- **Re-read before submit:** the open protective orders are re-read immediately before the stop is submitted, and the cover is
  recomputed from that read; if it changed, the new value is used (never more than the fresh gap allows).
- **Proof line:** `QHM <SYM> cover recovery: proved=N ledger_qhm=M broker=B protective_remaining=R stop=Q gap=G price=P action=sent|none`.
- **Result check after deploy:** broker long − Σ remaining valid protective sells is 0, or equals the gap the ACTION page reported.

## 2. The message standard (every trading alert)
Line 1 is the whole message on a phone lock screen, so it carries the verdict:

    <severity emoji> <SYMBOL> · <what happened, plain words>
    Money at risk: <only when true — shares, $ value, what could happen>
    Bot is: <what it is doing now>
    You: <one exact action, or "Nothing.">
    <tier> · <time PT>

Severity, one emoji each, nothing else:
- 🔴 ACTION: the owner must act, or money is unprotected and the bot cannot fix it itself. `You:` is never "Nothing."
- 🟠 HEADS-UP: something is wrong and the bot is handling it.
- 🟢 / ⚪ INFO: fills, stop raises, reports. No action. Sells use ⚪ so red only ever means ACTION.

Never in Slack: broker JSON, error codes, order/lot ids, Python exceptions, internal state or config names. They stay in the log. A
scrubber in the shared layer is the backstop (it removes `{…}` JSON bodies, uuids, `coid`s, exception reprs and ALL_CAPS_STATE names,
and logs a warning naming the call site so the template gets fixed).

## Changes after review round 3 (Codex: C1 resolved; C2 ordering impossible as written)
| # | Finding | Change |
|---|---|---|
| C2b | A boolean passed into the broker call cannot depend on a QHM send that happens after that call returns | Replaced by DEFERRED broker paging. The broker stop call takes `defer_failure_page=False` (default: today's behaviour). Only the dip-add restore (`_restore_or_pending`) passes True. With True, on a stop failure the broker sends the ntfy phone push at once (never deferred), does NOT send the Slack page, and returns the failure details (symbol, side, stop price, reason) to the caller. QHM then sends its one consolidated incident. In a `finally`, if that send did not report delivery (no alerter, webhook error, any exception, or QHM never reached the send), QHM calls `alerts.alert_gtc_failed(...)` with the returned details, so the Slack page still goes out. Tests: (a) dip-add failure + QHM send delivered → exactly one Slack incident post set and one ntfy push; (b) dip-add failure + QHM send fails → broker fallback page delivered; (c) exception between the broker return and the QHM send → fallback page delivered; (d) every other QHM / tier stop caller → broker page exactly as today. |
| N6 | Join key | The incident id is written to both `slack_sent.jsonl` and the matching app-log line. |
| N7 | "Exactly one" | Means one logical incident; a split message is one incident with N parts, logged as one row after all parts succeed. Tests cover a split message and two processes appending at once. |

## Changes after review round 3b (Codex APPROVE-WITH-CHANGES; implementation requirements)
- `failure_details = None` and `qhm_delivered = False` are set before the deferred broker call; the `try/finally` starts before that call
  and covers the call, the result handling and the consolidated send; the fallback runs only if `failure_details is not None and not
  qhm_delivered`.
- Tests check the fallback's arguments against the broker's returned details, and a regression test proves every non-dip-add caller
  leaves `defer_failure_page=False`.
- "Exactly one" means one logical incident. A webhook that accepts a post but times out before the client sees success can still
  duplicate (today's at-least-once behaviour); the incident id makes that visible.
- The first-session audit compares incident ids across `mtf_bot.log` and `slack_sent.jsonl`, `delivered: false` rows included.

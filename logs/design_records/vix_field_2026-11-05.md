## 1. Problem (code-traced; frequency unmeasured — server logs not readable from the cloud session)
`RegimeDetector._refresh` (`strategy/volatility_regime.py:109-142`) puts the VIX level (`:119`) or, when the Yahoo
fetch fails, SPY 10-day realized vol (`:128`) in one field, `realized_vol`. When both fail it keeps the old value with no
age limit (`:125-127`). `_fetch_vix` (`:84-92`) takes the last non-null close of a 5-day range and never checks its
timestamp, so yesterday's close can pass as today's VIX. A second VIX feed runs separately inside the macro risk gauge
(`events/macro_risk_index.py:623-660`: FMP T2 `^VIX` → 30-min cache → yfinance T4), so one cycle can hold two VIX values.
The fallback line is logged at INFO, which the midday audits do not sample, so fallback days have never been visible.

Every reader of the mixed number treats it as VIX:

Mechanism example (illustrative numbers, not a logged day): Yahoo fails on a calm day with VIX 17 and SPY RV10 11 → the
< 14 gate raises the core minimum score from 8 to 10 (fewer entries). On a stress day with VIX 36 and RV10 28 → stops
wait 3 bars instead of 1 after a breach, the stressed partials and BoD-4 stay off, and the allocator stays "stressed"
instead of "crash". [hypothesis — unverified: realized vol usually sits below VIX and lags it at a shock's onset.]

## 2. Fix
1. **One VIX provider** (`data/vix_provider.py`), shared by RegimeDetector and the macro risk gauge. Order:
   1. FMP `^VIX` (T2);
   2. Yahoo chart (T4), with the as-of time taken from the response's bar timestamp / `meta.regularMarketTime`, never
      the fetch time;
   3. the last VIX reading no more than one session old (age logged);
   4. a VIX-equivalent from SPY data (item 3);
   5. none.
   A reading counts as fresh only if its own timestamp is in the current session (pre-open: the last close).
2. **Separate fields, no silent redefinition.** `get_regime()` adds `vix`, `vix_asof`, `vol_source`
   (`fmp` / `yahoo` / `last_close` / `equivalent` / `none`), `spy_rvol_10d`. `regime_state.json` / `regime_history.jsonl`
   get the same fields plus a schema version; rows before the cut-over are tagged `mixed`. `realized_vol` keeps its old
   behaviour until every reader has moved, then is retired.
3. **VIX-equivalent (last resort, must earn its place in the replay).** Closed daily bars only, same feed for calibration
   and live (`fetch_closed_bars`); calibration window excludes today; computed pre-market, cached atomically with its
   as-of date and sample count. Candidates, chosen by replay error only: median VIX/RV10 ratio; log VIX on log RV10;
   log VIX on log RV10 + today's SPY intraday realized vol from closed minute bars + |SPY return| (catches a shock's
   first day, when RV10 lags). It publishes a point estimate and an error band. Kept only if its cut-off
   misclassification rate beats a one-session-old VIX.
4. **Every reader R1-R10 calls `vix_for_rules()`.** The allocator (R10) moves to the new `vix` field, so its 35 stays a
   VIX cut-off (redefining the field as realized vol would silently change when "crash" allocation fires).
5. **When there is no value**: readers keep receiving a float (0.0 sentinel plus `vol_source`), so the existing float
   comparisons cannot raise; each site gets a test. Behaviour with no value: R1, R6, R9 base settings; R2, R3 normal
   settings; R5 off; R7/R8 no widening; R10 cannot reach "crash"; R11 NORMAL with `fresh=False`. One Slack alert per
   day and a WARNING log whenever the source is not a live feed.
6. **Logging.** `VOL vix=… asof=… source=… spy_rvol10=… equiv=… band=… calib_asof=… n=…` at every refresh (WARNING when
   not `fmp`/`yahoo`), and `vix` + `vol_source` on every gate and exit line R1-R10 and on the entry record.
7. **No threshold changes.** 12 / 14 / 20 / 22 / 25 / 30 / 35 and the correlation thresholds stay as they are; replacing
   them with percentiles of the clean series is the REGIME-SIZE / regime phase-2 item this unblocks.

## 3. Open point (for GAI + Codex, then the owner)
**R4 stop confirmation when the reading is the equivalent or none.** Taleb/Thorp: lean protective — 1 bar when there is
no value or the equivalent's band crosses 30, because waiting 2 extra bars lets a real loss run past the planned stop on
exactly the day the feed is most likely to fail; it adds no trades and hides nothing. McKinney/Majors: base setting (3
bars) is acceptable. Check first whether the broker-side stop already sits at the planned stop (`exit_logic.py:81`,
`:367`); if it does, R4 is moot either way.
